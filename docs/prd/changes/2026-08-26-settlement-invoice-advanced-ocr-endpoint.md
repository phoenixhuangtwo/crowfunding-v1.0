# 增量 PRD：项目结算发票切换高精版 OCR 接口

- 状态：merged
- 日期：2026-08-26
- 发起人：用户浏览器批注 / Codex 实现
- 需求落点：增强现有模块（更换发票 OCR 供应商接口并适配识别全文）
- 涉及章节：01-内部资金认购平台 §4.9、§6、§7、§9、§10
- 实现关联：`server/invoice-ocr.ts`、`tests/invoice-ocr.test.ts`、`tests/smoke.mjs`、`.env.example`

## 一、需求背景与目标

项目结算页原发票 OCR 接口需要切换到阿里云高精版 OCR。若只更换调用地址而不调整协议，上传后会因请求格式和返回结构不同而识别失败。本次目标是让财务继续使用原上传入口，并看到新接口返回的真实识别全文与可提取的票面金额。

## 二、目标用户与使用场景

- 目标用户：负责项目结算的财务人员。
- 使用入口：项目管理 → 去结算 → 确认发起结算 → 上传发票。
- 主流程：选择发票图片后，系统通过服务端调用高精版 OCR，并展示识别全文；识别到“价税合计”“小写金额”等金额标签时同步展示金额。
- 异常场景：认证失败、套餐无权限、接口限流、图片不合规或未识别到文字时，页面保留原图并展示错误，允许重新上传。

## 三、用户可见方案

1. 发票上传入口、图片预览和识别中状态保持不变。
2. 识别成功后展示高精版 OCR 返回的实际识别全文，不再依赖旧接口的结构化发票字段。
3. 识别全文包含明确金额标签时，页面额外展示提取出的票面金额；无法可靠定位金额时不显示虚假金额。
4. 识别失败时保留发票原图并显示可理解的供应商错误。

## 四、边界与非目标

- 本期不新增发票验真、重复票识别、自动结算或发票图片持久化。
- 通用高精版 OCR 只负责文字识别，识别内容仍由财务核对，不自动替代人工结算判断。
- AppCode、AppKey、AppSecret 等认证信息不得进入浏览器或前端构建产物；本期使用服务端 APPCODE 认证，不启用 AppKey 与 AppSecret 签名认证。

## 五、验收标准

1. 服务端默认向 `https://gjbsb.market.alicloudapi.com/ocrservice/advanced` 发起 POST 请求。
2. 请求使用 `application/json; charset=UTF-8`，图片 Base64 位于 `img` 字段，且不包含 Data URL 前缀。
3. 认证仅通过服务端 `Authorization: APPCODE ...` 请求头发送。
4. 成功响应中的 `content` 或 `prism_wordsInfo` 能归一化为“识别全文”并在页面展示。
5. 识别全文存在明确金额标签时正确解析带千分位与两位小数的金额；不存在时不伪造金额。
6. 供应商错误、空识别结果、格式和大小校验均有明确反馈，全量测试与构建通过。

## 六、方案与取舍

保留现有 `/api/invoices/ocr` 服务端代理，前端不感知供应商切换。适配层将新接口的通用文字结果归一化为现有页面可消费的字段，减少页面改动；金额仅从明确标签附近提取，以降低把税额、单价等其他数字误判为价税合计的风险。

## 七、章节变更草案

修改 §4.9：发票 OCR 改由服务端代理高精版接口，成功后展示实际识别全文，并在存在明确金额标签时展示提取金额；异常时保持原图和重试能力。修改 §6、§7 和 §9 的接口说明、安全边界及验收口径。

## 八、影响面清单

- 权限点：不涉及，沿用财务结算权限。
- 菜单：不涉及。
- DataScope（数据范围）：不涉及。
- 状态口径：不改项目与结算状态，仅保留页面识别中、成功、失败状态。
- 通知：不涉及。
- 搜索：不涉及。
- 后台任务：不涉及，仍为单次同步请求。
- AI 边界：OCR 只提供识别结果，财务保留核对与结算决定权。
- 多端：当前 Web 页面生效；无独立移动端实现。

## 九、开放问题

- 高精版 OCR 仅提供通用文字识别，后续如需发票验真和稳定结构化字段，应另行评估专用发票识别或验真服务。
- 生产环境的超时重试、调用量监控和套餐配额告警待后续确认。
