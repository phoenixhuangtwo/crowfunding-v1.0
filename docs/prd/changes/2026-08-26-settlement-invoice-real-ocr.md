## 一、需求背景与目标

项目结算页已能预览财务人员实际上传的发票，但金额与字段仍是模拟结果，无法用于真实核对。本次接入发票 OCR（光学字符识别）服务，让财务在同一页对照原图、识别金额和返回字段。

## 二、目标用户与使用场景

- 目标用户：负责项目结算的财务人员。
- 入口：项目管理 → 去结算 → 确认发起结算 → 上传发票。
- 主流程：选择支持的图片后自动识别，并在原图旁展示识别内容。
- 异常场景：格式不支持、超过 5MB、服务未配置或供应商识别失败时，保留原图预览并显示可理解的错误，允许重新选择。

## 三、用户可见方案

1. 上传后立即显示实际发票原图与文件名，同时显示“识别中”。
2. 识别成功后，展示接口实际返回的价税合计金额及字段列表，不再用项目销售金额伪装 OCR 结果。
3. 识别失败后，显示供应商返回的业务错误，原图仍可放大核对。
4. 发票识别支持 PNG、JPG/JPEG、BMP，单张不超过 5MB。

## 四、边界与非目标

- 本期不做发票验真、重复票检测、发票图片持久化或自动完成结算。
- OCR 是可独立失败的外部可选集成；失败不覆盖项目、认购或结算试算数据。
- 认证信息只保存在服务端环境配置，不下发给浏览器。

## 五、验收标准

1. 上传有效发票图片后，服务端只向配置的 OCR 地址发起一次 POST 请求。
2. 浏览器请求和构建产物中不包含 AppCode、AppKey 或 AppSecret。
3. 识别成功后页面显示实际金额、任务号与返回字段；无金额时不显示虚假金额。
4. 识别失败时显示明确错误，并保留已读取的原图预览。
5. 格式、大小、代理请求、字段归一化与全量回归测试通过。

## 六、方案与取舍

采用本地 Node.js API 代理外部 OCR，前端只提交图片 Data URL（数据地址），服务端移除前缀并以 Base64 参数请求供应商。这保护认证信息，也将供应商返回格式与前端展示解耦。

## 七、章节变更草案

修改 §4.9：发票上传后调用服务端真实 OCR 代理，页面展示实际识别金额、任务号与所有可展示字段，异常时保留原图并提示。在 §6 新增 `/api/invoices/ocr`，在 §7 明确认证信息的服务端边界。

## 八、影响面清单

- 权限点：不新增，沿用财务结算入口。
- 菜单：不涉及。
- DataScope（数据范围）：不涉及。
- 状态口径：只新增页面识别中/成功/失败态，不改项目或结算业务状态。
- 通知：不涉及。
- 搜索：不涉及。
- 后台任务：不涉及，为当次同步请求。
- AI 边界：OCR 只产出识别结果，财务保留核对与结算决定权。
- 多端：当前 Web 页面生效；无独立移动端实现。
