## 一、需求背景与目标

员工进入支付页面后，左侧卡片只显示规则绑定的收款码信息，无法在付款前核对该收款码对应的实际认购项目。通用收款主体和账户说明容易被误认为项目本身的信息。本次在同一卡片中补充当前认购对应的实际项目、金额和规则数据，帮助员工确认“为哪个项目、按哪条规则、支付多少钱”。

## 二、目标用户与使用场景

- 目标用户：进入支付页核对收款信息的员工。
- 使用入口：我的认购 → 去支付、查看支付或重新上传截图。
- 触发场景：员工扫码或转账前核对当前认购和收款码的对应关系。
- 正常状态：认购记录能够匹配项目和已启用规则。
- 异常状态：项目或规则缺失时沿用现有明确提示，不使用其他项目数据兜底。

## 三、用户可见方案

“项目收款码”卡片分为当前认购项目和项目绑定收款码两部分。项目部分展示实际项目名称、项目编号、项目来源、项目成本金额、本次应付金额和认购规则；收款码部分继续展示规则绑定的图片、主体、名称、账户说明和编号。所有项目字段随当前认购记录切换，不使用固定项目文案。

## 四、边界与非目标

- 不把采购项目字段当作收款主体或收款账户信息。
- 不修改项目、规则、收款码或认购记录的数据。
- 不改变支付截图上传、OCR（光学字符识别）和财务复核流程。
- 不新增外部接口、通知、搜索、后台任务或 AI（人工智能）决策。

## 五、验收标准

1. 从“中国家庭医生”认购记录进入支付页，卡片展示项目名称、`PRJ-FSY-OFFLINE-368`、实际项目来源、项目成本金额、本次应付金额和“中国家庭医生”规则。
2. 切换其他认购记录时，项目区同步显示该认购对应的数据，不保留上一项目内容。
3. 收款码区仍严格展示当前项目规则绑定的收款码，不跨项目回退。
4. 项目或规则不可用时沿用明确空状态，支付上传与 OCR 流程不受影响。

## 六、方案与取舍

采用“项目上下文 + 收款码信息”分区，而不是用项目名称替换收款主体。这样既能满足项目核对，也保持收款账户字段的真实语义；采购接口未提供收款账户信息时，不编造项目专属收款主体。
