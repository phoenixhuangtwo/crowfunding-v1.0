## 2. 角色及授权规则

| 角色 | 业务编码 / IAM 编码 | 职责与边界 |
|---|---|---|
| 员工 | employee / crowdfunding_employee | 认购、缴款、查看本人收益及退款、本人确认到账 |
| 项目管理员 | admin / crowdfunding_admin | 同步采购、配置规则、发布和维护本人归属项目；无财务复核权 |
| 财务 | finance / crowdfunding_finance | 缴款复核、采购付款、回款、分配、退款及财务凭证；无公司专属复核权 |
| 公司超级管理员（公司） | super_admin / crowdfunding_super_admin | 公司兜底、公司复核、协议和参数、风险与审计；不自动继承管理员、财务的全部写权限 |
| 系统任务 | system（需求角色） | 自动兜底、状态推进、通知、审计写入；不作为普通交互登录角色 |

服务端当前要求四类交互角色恰好匹配一个；同时具有多类众筹角色会返回 `IAM_ROLE_INVALID`，不能用叠加多个角色来拼权限。

实际可操作 = 有效 IAM 登录 ∩ API 权限决策通过 ∩ 业务角色允许 ∩ 数据归属允许 ∩ 当前状态/金额/复核分离条件满足。

菜单可见还要求：IAM 返回对应菜单 componentName、对应 uiPermissions，且不被前端隐藏规则排除。按钮主要使用 apiPermissions；有菜单不代表有按钮，有按钮权限也不代表服务端必然允许。

## 6. 数据范围、凭证与系统任务

- 员工：必须具有 self 或 all 范围；本人认购、收益、退款仍按业务 userId 校验，不能因 all 就操作他人的确认。
- 管理员：非全范围仅少量 GET 被放行（项目、规则、认购、收款码、采购详情、文件）；实际列表进一步依归属处理，不等于所有部门数据均可用。写操作当前要求 all，此外还有本人归属检查。
- 财务、公司：除本人通知等例外，当前业务入口要求 all；部门数据迁移未完成时返回 `DATA_SCOPE_MIGRATION_REQUIRED`。
- 文件：`GET /api/files/:id/content` 的 access 权限只是入口；还要按文件用途、本人认购/退款、财务或公司角色校验。不能给 access 后就读所有凭证。
- 公司角色读取 ready 文件有较宽权限；员工收款码与支付/分配/退款凭证受业务关联限制，管理员没有通用财务凭证读取权。
- 系统任务不走前端菜单。自动兜底、超时释放、发布推进、通知生成、审计写入应由内部受控任务触发；当前交互角色解析不接受 system。

## 7. 需求与实现差异、待确认项

| 项目 | 文档/需求口径 | 当前静态实现 | 处理建议 |
|---|---|---|---|
| SRS 版本 | 仓库 SRS 描述 JSON 存储、模拟身份；验收引用另一个 V1.1 SRS | 当前为 MongoDB + IAM | 先确认众筹1.0正式需求原文，再更新需求基线 |
| 员工/管理员审计 | SRS 允许员工本人相关、管理员查询 | 全量日志接口拒绝员工和管理员；无独立本人审计入口 | 补受限查询或修订需求，禁止直接开放全量 |
| 管理员项目结算只读 | SRS 允许管理员 R | 试算仅财务/公司；隐藏侧栏且行内入口检查 upload-invoice | 区分只读结算与上传凭证权限 |
| 管理员支付复核只读 | SRS 允许管理员 R | 行内入口检查 query，管理员列表按归属过滤 | 用真实管理员核对只读页面加载所需 API，避免为可见入口授写权限 |
| 权限管理 | SRS 允许公司 C/R/U | rbac 菜单隐藏、白名单无 rbac；无角色授权修改 API | IAM 侧管理授权；明确业务系统是否只展示矩阵 |
| 风险维护 | SRS 允许公司 C/R/U | 权限注册仅 risk:query；无对应维护 API | 补需求映射或标为未交付 |
| 公司复核中心 | V1.1 记录要求统一复核 | 分散在回款、成本、代确认等模块；统一中心未完成 | 列齐复核事项，另补冲正及财务本人缴款公司复核 |
| 多角色兼任 | 可能期待财务同时作为员工认购 | 当前多类角色会被拒绝；认购只许 employee | 先明确身份/职责切换与禁止自审规则，不直接叠加角色 |
| 部门管理员操作 | IAM 可配置部门范围 | 受限管理员写操作仍被门禁阻断 | 不把已有 API 授权表述成部门写操作可用 |
| API 权限粒度 | receiving-code:disable 名称是禁用 | 启用也共用同一码 | 明确共用策略，或后续拆分 enable 权限 |
| 采购失败页面 | 管理员申请、公司复核、财务退款各有职责 | 页面通过 canQueryRequests 等条件按权限分别加载；申请列表 API 只允许管理员/公司 | 已为财务分配页面 UI 权限和退款 API，保持申请列表 API 不授予财务 |
| IAM 实际授权 | SQL 记录部分本地授权 | 初版未查；后续已核对当前数据库、Redis 和在线 RPC，员工/财务另有真实登录验证 | 配置前逐角色导出 menus/uiPermissions/apiPermissions/dataScope 做交叉复核 |

建议人工复核：正式 V1.1 需求原文、财务兼任员工、公司复核职责及管理员数据范围。本清单不构成多角色实测验收通过结论。

### 8.1 注册表以外的认证与动态权限

- `GET /api/health`：公开健康检查，不作为业务菜单授权。
- `GET /api/auth/login`：发起 OAuth 登录。
- `POST /api/auth/callback`：OAuth state/PKCE 校验与换取令牌。
- `POST /api/auth/refresh`：使用受控刷新 Cookie。
- `POST /api/auth/logout`：Bearer 令牌注销。
- `POST /api/subscriptions/:id/review`：注册入口码是 payment-review:query；服务端还根据 result/action 追加检查 approve/reject/partial。三项操作码因此不会单独表现为三条 URL。
- payment-proof:upload、payment-proof:query、settlement:query、takeover:query 等已声明权限不一定有一一对应的独立路由；上传操作可能由带文件的既有接口完成。配置时必须核对调用方式，不能按名称臆造 URL。
- 未登记方法/路径默认拒绝；代码注册不等于 IAM 已给某个角色授权，也不等于每条路由均完成业务验收。
